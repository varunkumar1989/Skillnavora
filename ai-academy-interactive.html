Starter script: call a model API with retries

import os, time, requests
def call(prompt, tries=3):
    for i in range(tries):
        r = requests.post(URL, headers={"Authorization": f"Bearer {os.environ['API_KEY']}"},
                          json={"model": MODEL, "messages": [{"role": "user", "content": prompt}]}, timeout=60)
        if r.status_code == 200: return r.json()
        if r.status_code in (429, 500, 502, 503): time.sleep(2 ** i); continue
        r.raise_for_status()
    raise RuntimeError("model API unavailable")

Intermediate · Class 4

LLM engineering: model APIs, prompts, structured output, cost and latency

Build reliable features on top of model APIs.

  • Providers: Anthropic Claude, OpenAI, Google Gemini, plus open models (Llama, Mistral, Qwen, DeepSeek) via Hugging Face, Ollama, vLLM, Groq, Together.
  • Key parameters: system prompt, temperature/sampling (where supported), max tokens, stop sequences, streaming, tool definitions, structured outputs/JSON schema.
  • Tokens & context: price per input/output token, context window limits, prompt caching, batching for cost.
  • Reliability: timeouts, retries with backoff, provider fallbacks, circuit breakers, idempotency.
  • Quality: few-shot examples, chain-of-thought where useful, self-checks, guardrails.
  • Cost & latency: route simple tasks to small models, cache, trim context, stream for perceived speed. Track cost per successful task.
cost per request = input_tokens × price_in + output_tokens × price_out
latency budget   = retrieval + model + tools + post-processing   (set a target for each)

Key takeaways
  • Treat the model as an unreliable remote service: validate, retry, fall back.
  • Track tokens, cost and latency on every call.
  • Structured outputs make LLMs usable in code.

Intermediate · Class 6

Agents, tool use and MCP

Build agents that call tools, with control and observability.

  • Tool/function calling: describe tools with JSON schemas; the model returns structured calls; your code executes and returns results.
  • MCP (Model Context Protocol): standard way to expose tools and data to AI assistants; build MCP servers for your product; use existing ones (GitHub, Slack, Playwright, databases).
  • Frameworks: LangGraph, LangChain, LlamaIndex, OpenAI Agents SDK, Claude Agent SDK, CrewAI, AutoGen, Pydantic AI; or plain code (often the best start).
  • Patterns: chaining, routing, parallel, orchestrator-workers, evaluator-optimizer (see Orchestration course).
  • Memory: short-term (conversation), long-term (vector store/db), summaries, user profile.
  • Control: step/cost limits, approvals for risky tools, sandboxing code execution, tracing every run.
  • Computer & browser use: Playwright MCP, Browser Use (see Web Automation course).

Advanced · Class 7

Customising models: fine-tuning, distillation and open-source models

Decide when to fine-tune, and how, and when not to.

MethodWhen
Better prompts and examplesAlways first
RAGKnowledge changes or is private; need citations
Supervised fine-tuning (SFT)Consistent style/format, domain behaviour, shorter prompts, cost reduction
LoRA / QLoRAParameter-efficient tuning of open models on one GPU
Preference tuning (DPO, RLHF concepts)Align outputs with human preferences
DistillationTeach a small, cheap model from a large one's outputs

Fine-tuning workflow

  1. Collect 500–5,000 high-quality examples (inputs and ideal outputs); clean and split train/validation/test.
  2. Baseline with prompting; define eval metrics first.
  3. Fine-tune (provider fine-tuning APIs, or Hugging Face Transformers, PEFT, TRL, Unsloth, Axolotl).
  4. Evaluate against the baseline on held-out data; check regressions and safety.
  5. Deploy (vLLM, TGI, Ollama, or provider-hosted); monitor drift; retrain on new data.

Learn it here: Customising models: prompting vs RAG vs fine-tuning, LoRA · ML Products for PMs

Key takeaways
  • Prompting → RAG → fine-tuning, in that order.
  • Data quality beats data quantity.
  • Always compare with a prompting baseline.
Practice: Plan (data, metric, baseline, hardware, evaluation) a LoRA fine-tune for classifying support tickets.
Advanced · Class 8

Evals, observability, guardrails and red-teaming

Make quality measurable and keep it that way.

  • Evals: golden dataset, code and LLM-judge graders, human review, regression suite in CI (see AI Evals course).
  • Observability: trace every request (prompt, retrieved docs, tool calls, tokens, cost, latency); tools: Langfuse, LangSmith, Arize Phoenix, Braintrust, OpenTelemetry.
  • Guardrails: input checks (PII, injection), output checks (schema, toxicity, policy), allow-lists for tools, rate limits; libraries such as Guardrails AI, NeMo Guardrails, Llama Guard, provider moderation APIs.
  • Red-teaming: jailbreaks, prompt injection, data exfiltration, harmful content, bias tests; add each finding to the eval set.
  • Online quality: sample live traffic, judge scores, user feedback, A/B tests.

Key takeaways
  • No eval, no launch.
  • Trace everything to debug fast.
  • Guardrails are layers, not a single filter.

Advanced · Class 11

System design for AI products and working with the team

Design end-to-end AI systems and collaborate across roles.

How to answer an AI system-design question

  1. Clarify users, scale, languages, latency and quality targets, risks.
  2. Sketch the architecture (above) and the data flow.
  3. Pick approaches with trade-offs: prompting vs RAG vs fine-tune; one model vs routing; sync vs async.
  4. Cover evals, safety, observability, cost and failure handling.
  5. Discuss rollout: shadow, canary, A/B, human fallback.

Common designs to practise

  • Customer-support copilot (RAG + tools + handoff)
  • Document processing pipeline (OCR → extraction → validation → human review)
  • Voice agent for appointments (STT → LLM → TTS, barge-in, latency)
  • Code assistant (indexing, context selection, sandbox, tests)
  • Internal knowledge search with permissions
  • Recommendation or search ranking with LLM reranking

Working with PMs, designers and data teams

  • Turn PRDs into eval sets and acceptance criteria; push back with data on feasibility and cost.
  • Demo early with real outputs including failures; document assumptions and limits.
  • Be on-call for AI quality: incident reviews, postmortems, new tests.

Key takeaways

  • Evals, safety and cost belong in every design.

12 interview questions with answers

What does an AI engineer do?

Builds, evaluates, deploys and operates AI-powered software: model APIs, RAG, agents and tools, evals, guardrails, cloud deployment and monitoring, with attention to cost, latency and safety.

AI engineer vs ML engineer?

AI engineers mostly build products on existing models (prompts, RAG, agents, evals); ML engineers train and serve custom models and run ML pipelines. The roles overlap.

How would you design a RAG system?

Ingest and chunk documents with metadata, embed, store in a vector DB, retrieve with hybrid search and reranking, generate with citations, enforce access control, evaluate retrieval and faithfulness, monitor and refresh.

When do you fine-tune?

After prompting and RAG fall short: for consistent style or format, narrow tasks, or to lower cost with a smaller model; compare to a prompting baseline on held-out data.

How do you evaluate an LLM application?

Golden dataset with slices, code and LLM-judge graders calibrated to humans, regression tests in CI, online metrics and sampled judging.

How do you reduce hallucinations?

Ground answers in retrieved sources, require citations and 'not found', use structured outputs, add verification steps and evals, and escalate low-confidence cases.

How do you control cost and latency?

Route to smaller models, cache, trim context, stream, batch, set budgets, and track cost per successful task.

What are the main security risks of LLM apps?

Prompt injection, data leakage, insecure output handling, excessive agency, supply chain and denial of wallet; mitigate with least privilege, validation, sandboxing, approvals and rate limits.

Explain MCP.

The Model Context Protocol standardises how AI assistants connect to tools and data; you can build MCP servers to expose your product and use existing ones.

Walk through deploying an AI service.

FastAPI service in Docker, CI with tests and evals, deploy to cloud, gateway for auth/limits/routing, tracing and alerts, canary rollout and rollback.

How do you handle a quality regression in production?

Check traces, compare against the eval set, identify cause (prompt, retrieval, model update, data drift), roll back, fix, add a regression test.

What projects would you show in a portfolio?

A cited RAG app, an agent with tracing, an eval harness in CI, a deployed service with monitoring, and a fine-tune vs prompt comparison.

Building reliable webhook receivers

Verify, process and retry webhooks safely in production.

Six rules for production webhooks

  1. Verify the signature (HMAC) so only the real provider can call you.
  2. Respond fast (200 OK within a few seconds); do heavy work in a queue.
  3. Be idempotent: providers retry, so the same event may arrive twice; store event IDs and skip duplicates.
  4. Handle retries and order: events can arrive late or out of order; check current state.
  5. Log everything: raw payload, headers, result; keep a replay option.
  6. Secrets in environment settings, never in code.

Signature check (Node.js / Cloudflare-style function)

import crypto from "node:crypto";
export async function onRequestPost({ request, env }) {
  const body = await request.text();                       // raw body, before JSON parsing
  const sig = request.headers.get("x-razorpay-signature") || "";
  const expected = crypto.createHmac("sha256", env.RAZORPAY_WEBHOOK_SECRET).update(body).digest("hex");
  if (sig.length !== expected.length ||
      !crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected)))
    return new Response("invalid signature", { status: 401 });
  const event = JSON.parse(body);
  // idempotency: skip if this event id was already processed (check your DB/KV)
  // enqueue the work, then reply quickly
  return new Response("ok");
}

Each provider documents its own header name and signing method; follow its official guide.

Local testing

Expose your laptop with a tunnel (ngrok, Cloudflare Tunnel) or use the provider's CLI to forward test events; replay saved payloads in tests.

Key takeaways
  • Verify signatures, respond fast, be idempotent.
  • Expect retries and out-of-order events.
  • Log and replay for debugging.

Playwright for browser automation

Automate any website reliably with Playwright.

Playwright (by Microsoft) controls Chromium, Firefox and WebKit from Python, JavaScript/TypeScript, Java or .NET. It auto-waits for elements, records your clicks as code and replays failures step by step.

Setup and record

pip install playwright && playwright install chromium
playwright codegen https://demo.playwright.dev/todomvc/     # click around; code is written for you

Script: log in, export a report (pattern)

from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    ctx = browser.new_context(storage_state="auth.json")   # reuse a saved, authorised login
    page = ctx.new_page()
    page.goto("https://portal.example.com/reports")
    page.get_by_label("From").fill("2026-10-01")
    page.get_by_role("button", name="Export CSV").click()
    with page.expect_download() as d:
        page.get_by_role("link", name="Download").click()
    d.value.save_as("report.csv")
    browser.close()

Make it robust

  • Locate by role, label, text or test id, not fragile CSS paths.
  • Use storage_state for logins (store securely; never commit it).
  • Turn on tracing; open failures in the trace viewer.
  • Run on a schedule (GitHub Actions cron, n8n Execute Command, a small server) with alerts on failure.
Key takeaways

Interview prep

10 interview questions with answers

What is a webhook?

An HTTP request an app sends to your URL when an event happens, so you get updates instantly instead of polling.

How do you secure a webhook endpoint?

Verify the provider's HMAC signature on the raw body, use HTTPS, keep the secret in environment settings, respond fast, and process idempotently.

Webhook vs polling?

Webhooks push instantly and save calls; polling checks repeatedly and adds delay but works when no webhooks exist.

What is idempotency and why does it matter?

Processing the same event twice has no extra effect; needed because providers retry and may send duplicates.

What is the Playwright MCP?

An MCP server by Microsoft that exposes browser actions (navigate, click, type, snapshot) so AI assistants like Claude can use a real browser.

Playwright vs Selenium?

Playwright: newer, faster, auto-waiting, multi-browser, great tooling and MCP. Selenium: mature standard with broad language and grid support, common in existing enterprise suites.

When would you use an AI browser agent instead of a script?

When pages change often or tasks vary; keep scripts for stable steps and add AI for the messy parts, with evals and approvals.

How do you schedule an automation for 9 am IST on weekdays?

Cron '0 9 * * 1-5' in IST, or '30 3 * * 1-5' if the server runs in UTC.

What risks come with browser automation?

Breaking on UI changes, terms-of-service and legal issues, credential leaks, prompt injection for AI agents, and irreversible actions; mitigate with APIs, sandboxes, approvals and monitoring.

From the attached invoice images, extract: vendor, GSTIN, invoice no., date (DD-MM-YYYY),

What an eval is, and why PMs own it

Understand evals as the unit test, the quality bar and the product spec for AI features.

The one-line definition

An eval (evaluation) is a repeatable test that measures how well an AI system does a specific job, on a fixed set of examples, with a clear way to score each answer. Run it before launch, after every prompt or model change, and on live traffic.

Why it matters: traditional software is deterministic (same input, same output), so unit tests are pass/fail. LLM features are probabilistic: the same question can get a different answer tomorrow, after a model upgrade, or with a small prompt edit. Without evals, a team ships on vibes and finds problems from angry users.

  • Evals are the spec. "Good answer" is a product decision: tone, accuracy, what to refuse, when to hand over to a human. If the PM doesn't define it, the model provider's defaults decide for you.

Grading methods: code, humans and LLM-as-judge

Choose the cheapest grader that measures what matters, and know when to use humans.

Three ways to grade

Code-basedExact match, regex, JSON schema, "contains", runs the SQL/code, checks lengthClassification, extraction, format, tool calls, mathCan't judge meaning or tone

Reference-based vs reference-free

Reference-based: compare to an expected answer (exact match, semantic similarity, "does it contain the key facts"). Reference-free: judge against the rubric or the source documents (e.g. "is every claim supported by the context?"). Older text metrics such as BLEU and ROUGE measure word overlap and correlate poorly with quality for chat answers; prefer rubric or fact-checking graders.

Writing a good LLM-judge prompt

You are grading a bank support reply.
Question: {question}
Policy excerpt: {context}
Reply to grade: {answer}

Check ONE criterion: Is every factual claim in the reply supported by the policy excerpt?
Think step by step, listing each claim and whether it is supported.
Then output exactly: {"pass": true|false, "unsupported_claims": [...]}
  • One criterion per judge call; binary output; ask for reasoning before the verdict.
  • Give the judge the source/reference it needs.
  • Use a strong model as judge, ideally different from the model being graded.

Known judge biases and fixes

BiasFix
Position bias (prefers answer A in pairwise)Run both orders; count a win only if consistent
Verbosity bias (prefers longer)Rubric says "length is not quality"; check conciseness separately

Calibrate the judge against humans

Have experts label 50–100 outputs. Compare with the judge: aim for ≥ 85–90% agreement and Cohen's kappa ≥ 0.6 before trusting it at scale.

agreement p_o = (both pass + both fail) / total
chance     p_e = P(human pass)·P(judge pass) + P(human fail)·P(judge fail)
kappa      κ  = (p_o − p_e) / (1 − p_e)

Example: 100 items; both pass 70, both fail 18, disagree 12
p_o = 0.88; human pass 0.76, judge pass 0.78
p_e = 0.76·0.78 + 0.24·0.22 = 0.646  →  κ = (0.88 − 0.646)/(1 − 0.646) ≈ 0.66

  • LLM judges scale open-ended grading but must be calibrated against humans.
  • One criterion per judge, binary verdict, reasoning first.

Error analysis: finding what actually breaks

Read outputs systematically, name the failure modes and fix the biggest ones first.

Why error analysis comes first

Teams often jump to fancy metrics. The highest-leverage activity is simpler: read 50–100 real outputs and write down what went wrong. Most products have 3–5 failure modes that cause 80% of the problems.

The method

  1. Sample 100 traces (input, retrieved context, tool calls, output), mixing random and flagged ones.
  2. Open coding: for each failed trace, write a short free-text note ("quoted old refund policy", "ignored that user already tried OTP").
  3. Axial coding: group notes into categories (outdated knowledge, missed context, wrong tool, tone).
  4. Count and rank categories by frequency × severity.
  5. Fix and add tests: for each top category, change prompt/data/retrieval/tools and add targeted eval cases.

Look at the whole trace

Evaluating RAG (retrieval-augmented generation)

Measure retrieval and generation separately, so you know which half to fix.

Two halves, two sets of metrics

StageMetricMeaning
RetrievalRecall@kShare of questions where a correct document is in the top k results
Precision@kShare of the top k results that are relevant
MRRAverage of 1 / rank of the first relevant document
GenerationFaithfulness / groundednessEvery claim is supported by the retrieved context

Citation accuracyCited sources actually contain the claim

Worked example: MRR and Recall@3

Question   rank of first relevant doc   1/rank   in top 3?
Q1         1                            1.00     yes
Q2         3                            0.33     yes
Q3         not found                    0        no
Q4         2                            0.50     yes
MRR = (1 + 0.33 + 0 + 0.5) / 4 = 0.46      Recall@3 = 3/4 = 75%

Diagnosing with the 2×2

Answer correctAnswer wrong
Right docs retrievedWorking ✔Generation problem: prompt, model, too much context
Wrong docs retrievedLucky / model knowledge (risky)Retrieval problem: chunking, embeddings, filters, query rewriting

Common RAG fixes

  • Better chunking (by heading, 300–800 tokens, with overlap) and metadata (product, date, region).
  • Hybrid search (keyword + vector) and re-ranking.
  • Query rewriting for short or Hinglish questions.
  • Instruction: "If the context doesn't contain the answer, say so and offer a human."
  • Freshness checks so old policies are removed from the index.

Open-source helpers: Ragas and DeepEval compute faithfulness, relevance and context metrics; always spot-check them by hand.

Key takeaways
  • Score retrieval and generation separately.
  • Faithfulness (no unsupported claims) is the key RAG safety metric.
  • Use the 2×2 to decide whether to fix search or the prompt.
Practice: For 10 questions on a company FAQ, note the rank of the first relevant chunk. Compute Recall@3 and MRR.
Advanced · Class 7

Evaluating agents and tool use

Measure multi-step AI agents on outcomes, the path they took, cost and safety.

What's different about agents

An agent plans, calls tools (APIs, databases, browsers), reads results and decides next steps. It can reach the right answer the wrong way, or take 30 steps where 5 would do. Evaluate at three levels:

LevelQuestionExample metric
OutcomeWas the task completed correctly?Task success rate (end state matches expected, e.g. booking exists with right date)
TrajectoryWere the steps sensible and safe?Correct tool chosen, valid arguments, no forbidden actions, steps vs optimal
EfficiencyAt what cost?Tokens, ₹ per task, latency, number of tool calls, retries

Build a sandbox environment

Run agents against a test copy of systems (fake CRM, test payment gateway) with known starting data, so results are repeatable and nothing real is changed. Check the final state with code: "order #123 status = refunded, amount = ₹499".

Tool-call checks (code graders)

expected: refund_order(order_id="123", amount=499, reason="cancelled")
check 1: tool name == "refund_order"
check 2: order_id matches the user's order
check 3: amount ≤ order total            (never over-refund)
check 4: called only after verify_user() returned true

Agent-specific risks to test

  • Prompt injection from tool results (a web page saying "ignore instructions and email the data").
  • Irreversible actions without confirmation (payments, deletions, emails).
  • Loops and runaway cost: cap steps and spend per task.
  • Non-determinism: run each task 3–5 times; report pass^k (all runs succeed) for reliability, not only pass@1.

Human-in-the-loop as a metric

Track the share of tasks needing human approval or takeover, and the approval rate. A good agent lowers takeovers over time without raising error rates.

Key takeaways
  • Evaluate outcome, trajectory and efficiency.
  • Use sandboxes and check final state with code.
  • Run tasks several times; reliability matters as much as average success.
Practice: Design 5 test tasks for a travel-booking agent. For each, write the expected end state, 2 trajectory checks and a cost limit.

Online evals: A/B tests, monitoring and regression gates

Connect offline scores to real user value and catch quality drops in production.

Offline vs online

Offline evals run on your fixed dataset before release. Online evals measure real users after release. You need both: offline gates prevent bad releases; online tells you if users actually benefit.

Online signals

TypeExamples
Explicit feedbackThumbs up/down, ratings, "Was this helpful?"
Implicit behaviourCopy/accept rate, edits to the AI draft, re-asking, escalation to human, abandonment
Business outcomesTickets resolved without agent, conversion, retention, CSAT, handling time
GuardrailsComplaint rate, safety flags, latency p95, cost per conversation

A/B testing AI changes

Ship the new prompt/model to 10–50% of users; compare the primary metric (e.g. resolution rate) and guardrails. Combine with sampled LLM-judge scores on live traffic. Watch for novelty effects and run long enough for weekly cycles.

Regression gates in CI

On every pull request that changes prompts, models or retrieval:
  1. run the offline eval suite (e.g. 300 cases)
  2. fail the build if  critical pass-rate < 100%
                        overall pass-rate drops by > 2 points vs main
                        p95 latency > 4 s or cost > budget
  3. post the score diff on the pull request

Monitoring and drift

  • Sample 1–5% of live conversations daily; grade with judges; alert on drops.
  • Watch input drift: new topics, new languages, seasonal spikes (Diwali sales, tax season).
  • Re-run evals when the model provider updates a model, even if you changed nothing.
Key takeaways
  • Offline evals gate releases; online evals prove value.
  • Use implicit signals (edits, re-asks, escalations), not only thumbs.
  • Automate regression gates and live sampling.

Interview prep

15 interview questions with answers

What is an eval and why does a PM care?

A repeatable test of AI quality on fixed examples with a scoring method. PMs define 'good', set launch bars and use evals to make model/cost trade-offs.

How would you evaluate an AI customer-support bot?

Define criteria (correct, grounded, private, resolves, escalates, tone); build a sliced golden set from real tickets; grade with code + calibrated LLM judges; set bars; then measure resolution rate, CSAT and escalations online.

What is LLM-as-judge and its risks?

Using a model to grade outputs against a rubric. Risks: position, verbosity and self-preference bias, leniency. Mitigate with binary criteria, swapping order, a different judge model, and calibration against human labels (kappa ≥ 0.6).

How many examples do you need?

30–50 to find obvious issues, 100–300 for a launch decision, more for fine comparisons. Margin of error ≈ 1.96√(p(1−p)/n).

How do you evaluate a RAG system?

Separately: retrieval (recall@k, MRR) and generation (faithfulness, relevance, citation accuracy). Use the 2×2 of right/wrong docs vs right/wrong answer to locate the fix.

How do you evaluate an AI agent?

Outcome (task success via end-state checks), trajectory (right tools and arguments, no forbidden actions) and efficiency (cost, steps, latency), in a sandbox, with repeated runs for reliability.

Offline vs online evals?

Offline: fixed dataset before release, used as gates. Online: real users after release via A/B tests, implicit signals and sampled judging.

A new model is 40% cheaper. Do you switch?

Run the full eval suite and slices; check critical criteria and safety; compare cost per successful task, not per call; A/B test on a slice of traffic with guardrails.

What is error analysis?

Reading real traces, labelling failures (open coding), grouping into categories, counting and fixing the biggest first, then adding tests.

How do you test for bias?

Counterfactual pairs that change only a protected attribute (name, gender, region, language) and compare outcomes and tone across many pairs.

What is over-refusal?

When the AI refuses valid requests that look risky. Measure it with benign-but-sensitive prompts; it hurts helpfulness and retention.

What goes into the eval section of a PRD?

Criteria and rubric, dataset plan, graders and calibration, launch bars, online metrics and guardrails, monitoring and red-teaming.

How do you stop quality from regressing?

Regression suite in CI on every prompt/model change, live sampling with alerts, re-running evals on provider model updates, and adding every incident as a test.

Precision vs recall for a fraud-flagging AI?

High recall catches more fraud but annoys good users with false alarms; high precision means fewer false alarms but missed fraud. Choose by cost of each error; often a human reviews the flagged set.

What metrics would you show leadership?

Quality pass-rate by critical criterion, safety incidents, resolution or task success, cost per successful task, latency p95, and user outcomes (CSAT, retention).

Software (scripts, RPA bots or AI agents) using websites to do tasks: navigate, click, type, extract data. Scripts follow fixed steps; AI agents pursue goals.

Script vs AI agent: when do you use which?

Scripts for stable, repeated, high-volume steps (cheap, reliable). Agents for varied or messy tasks where steps change. Prefer an API over both when available.

How does a computer-use agent work?

It loops: observe the screen or page, decide the next action, act (click/type/scroll), observe again, until the goal is met or it needs a human.

Biggest risk with browser agents?

Prompt injection from web content, plus irreversible actions. Controls: allow-listed sites, treat page text as data, approval before submit/pay/send, no secrets in prompts.

How would you evaluate a browser agent?

Sandbox tasks with known end states; measure task success, reliability over repeated runs, steps, time, cost per success, safety violations and human takeover rate.

Give a PM use case.

Weekly competitor pricing tracker, release smoke tests of key flows, research for a PRD, or QA of onboarding across devices.

What is Playwright codegen?

A tool that records your browser actions and writes the equivalent Playwright code, a quick way to start a script.

Is scraping legal?

It depends on the site's terms, the data and the law. Avoid personal data without a lawful basis (DPDP Act), respect robots.txt and rate limits, never bypass CAPTCHAs, and prefer official APIs.

How do deep research agents differ from browser agents?

Research agents search and read many pages to write a cited report; browser agents take actions on specific sites. Use research for breadth, browser agents or manual checks for depth.

How would you reduce cost of an agent workflow?

Use scripts for stable steps, agents only where needed; cap steps; cache pages; choose cheaper models for simple steps; measure cost per successful task.

What goes into a PRD for a browser-agent feature?

Scope and allowed sites, approval matrix, credential and data handling, success/reliability/cost/safety bars, monitoring and human fallback.

How do you make scripts less flaky?

Use role/label/test-id locators, rely on auto-waits, add assertions, run headless in CI with retries, and inspect failures in the trace viewer.

Orchestrator-workers and evaluator-optimizer

Use the two most powerful agentic patterns safely.

Orchestrator-workers

A lead model plans the work, sends sub-tasks to workers (other model calls or agents), then combines results. Good for research and analysis where sub-tasks aren't known in advance.

One model drafts, another evaluates against a rubric and gives feedback, loop until the bar is met or a step limit is reached. Good for writing, code and PRDs with clear quality criteria.

loop max 3 times:
  draft = writer(brief, feedback)
  review = evaluator(draft, rubric)      # returns pass + issues
  if review.pass: break
  feedback = review.issues
return draft, review

Always set limits (steps, time, cost) so loops end.
