LLMOps, evaluation and optimisation

Outcome: 20-question evaluation and quality report

Subject 13: AI evaluation

Covered on the website   Week 4 · Advanced technical knowledge

1. Understand

Evaluation is a driving test for an AI feature. You prepare a fixed set of questions with known good answers, run the system, and count how many it passes.

2. Why it matters

AI output changes when you change a prompt, a model or a document. Without a fixed test set you cannot tell whether a change made things better or worse.

3. How it works

  • Build a golden dataset: 20 or more questions with the expected answer or a checkable fact.
  • Score each answer: correctness, faithfulness (supported by the context), groundedness, retrieval precision and recall.
  • Automate simple checks (must contain a fact, must cite a source).
  • Use LLM-as-a-judge for subjective scores; check the judge against a few human ratings.
  • Re-run the set after every change (regression testing).

4. Practical implementation

File: tools/aihandbook/examples/06_eval_harness.py

# Week 4, Subject 13: a tiny evaluation harness with a golden dataset
GOLDEN = [
    {"question": "How many paid leave days per year?", "must_contain": "20"},
    {"question": "How many days can leave be carried forward?", "must_contain": "5"},
    {"question": "Who approves remote work?", "must_contain": "manager"},
    {"question": "What is the CEO's salary?", "must_contain": "not in the document"},
]

def system_under_test(question):
    answers = {
        "How many paid leave days per year?": "You get 20 days of paid leave.",
        "How many days can leave be carried forward?": "Up to 5 days.",
        "Who approves remote work?": "Your manager approves it.",
        "What is the CEO's salary?": "The CEO earns 5 crore.",  # a hallucination the test should catch
    }
    return answers[question]

passed = 0
for case in GOLDEN:
    answer = system_under_test(case["question"])
    ok = case["must_contain"].lower() in answer.lower()
    passed += ok
    status = "PASS" if ok else "FAIL"
    print(f"{status}  {case['question']}  ->  {answer}")
print(f"Score: {passed}/{len(GOLDEN)} ({passed / len(GOLDEN):.0%})")

Expected output (produced by running the file)

PASS  How many paid leave days per year?  ->  You get 20 days of paid leave.
PASS  How many days can leave be carried forward?  ->  Up to 5 days.
PASS  Who approves remote work?  ->  Your manager approves it.
FAIL  What is the CEO's salary?  ->  The CEO earns 5 crore.
Score: 3/4 (75%)

5. Code explained

  • GOLDEN is the test set. Keep it in version control.
  • must_contain is the simplest checkable rule.
  • The last case is a deliberate hallucination: the harness must mark it FAIL.

5b. Deep dive

Build the golden set from real questions: ask 10 people in the target role for their 5 most common questions, then write the expected answer and the source for each. Include edge cases and questions with no answer.

Metrics: answer correctness (human or judge score), faithfulness (is each claim supported by the retrieved context), context relevance (are the retrieved chunks useful), retrieval recall at k (was the right chunk in the top k), and refusal accuracy (did it decline when it should).

LLM-as-a-judge: a second model scores answers against a rubric. Calibrate it: have a person score 30 answers, then check the judge agrees most of the time. Judges prefer longer answers and their own style, so use a rubric that penalises padding.

Frameworks to explore after the basics: Ragas (RAG metrics), DeepEval (test-style checks), LangSmith (tracing and datasets). Learn the metric definitions first; tools change faster than concepts.

Subject 14: Hallucinations, guardrails and AI quality

Covered on the website   Week 4 · Advanced technical knowledge

1. Understand

A hallucination is a fluent answer that is not supported by the facts. The model is designed to continue text plausibly, not to check truth.

2. Why it matters

In customer support, finance or health, one confident wrong answer can cause real harm. Quality work reduces the chance and limits the damage.

3. How it works

  • Causes: missing context, ambiguous questions, pressure to answer, out-of-date training data.
  • Mitigations: grounding in retrieved sources, citation requirements, refusal when context is missing, confidence signals, fallback answers.
  • Guardrails: input checks (block unsafe requests), output checks (scan for personal data or claims without sources).
  • Prompt injection: instructions hidden in a document or web page that try to override your rules. Treat all retrieved text as untrusted data.
  • Human review: route low-confidence or high-risk answers to a person.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Refusal is a designed behaviour and must be tested like any feature.
  • Never let retrieved text change the system rules; keep instructions and data separate in the prompt.

5b. Deep dive

Hallucination types: made-up facts, wrong citations, confident answers to unanswerable questions, and mixing two sources into one wrong claim. Measure each type separately; each needs a different fix.

Guardrail layers: input checks (block personal data requests, prompt injection patterns), retrieval checks (minimum relevance score before answering), output checks (every claim has a citation, no personal data in the answer), and human review for high-risk topics.

Prompt injection: a retrieved page may say 'ignore your rules'. Defence: treat retrieved text as data, never as instructions; separate system instructions from data with clear delimiters; limit what tools can do; test with known attack strings.

Confidence signals: retrieval score, the share of claims with citations, and the model's own uncertainty statement. None is perfect alone; combine two and test them on the golden set.

Subject 15: Latency and cost

Covered on the website   Week 4 · Advanced technical knowledge

1. Understand

Every AI request has a price and a waiting time. You pay for tokens in and out, and users wait for the first word and the last word.

2. Why it matters

A feature that is accurate but takes 20 seconds, or costs more than the revenue it earns, will not survive.

3. How it works

  • Measure input tokens, output tokens, time to first token and total time.
  • Reduce cost: shorter context, caching repeated prompts, batching, smaller models for simple steps, model routing.
  • Measure cost per successful task: total spend divided by tasks that met the quality bar.
  • Trade off quality against cost: write the numbers into the PRD.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Output tokens usually cost more than input tokens; keep answers short when short is enough.
  • Streaming improves perceived speed even when total time is the same.

5b. Deep dive

Latency is the sum of parts: embedding the query, the database search, reranking, prompt building, the model's time to first token, and the time for all output tokens. Measure each part with timers before optimising.

Cost levers in order of impact for most products: shorter prompts (trim history, retrieve fewer chunks), smaller models for easy steps (classification, routing), caching identical requests, batching offline jobs, and limiting output length.

Cost per successful task: total spend divided by tasks that passed the quality bar. A cheap model with a 60 percent pass rate can cost more per success than a dearer model with 95 percent.

Set service targets before optimising: for example p95 latency under 8 seconds, cost under a fixed amount per resolved ticket, and quality above the golden-set bar. Optimise only when a target is missed.

Subject 16: LLMOps: running AI in production

Covered on the website   Week 4 · Advanced technical knowledge

1. Understand

LLMOps is the operations discipline for AI systems: logging what happened, watching quality and cost, versioning prompts and models, and rolling back when something breaks.

2. Why it matters

AI systems degrade quietly. A provider update or a changed document can reduce quality with no error message.

3. How it works

  • Log each request: prompt version, model, retrieved sources, tokens, latency, user feedback.
  • Version prompts and model names like code.
  • Monitor dashboards: quality sample, cost, latency, error rate, refusal rate.
  • Run the evaluation set on every release (regression testing) and before every model change.
  • Protect data: remove personal data from logs, manage API keys in a secret store, rotate keys.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • A prompt is production code: review it, test it and version it.
  • Logs must respect privacy rules; log IDs and metadata, and redact personal data.

5b. Deep dive

Logs: one structured record per request (JSON lines) with request id, prompt version, model name, retrieved chunk ids, token counts, latency, status and feedback. Redact personal data before writing.

Versioning: store prompts in files under version control with a version number; record the version in every log. Pin model names and check release notes when a provider changes a model alias.

Release gate: run the golden set, compare with the last release, block the release if any key metric falls below its bar, and keep a rollback path (the previous prompt and model version).

Operations basics: alerts on error rate, latency and cost spikes; a weekly quality sample reviewed by a person; an incident note for each failure with cause and fix.
