Week 3

AI agents, tool calling and MCP

Outcome: AI research agent

Subject 9: AI agent fundamentals

Covered on the website   Week 3 · Core practical skills

1. Understand

An agent is a chatbot that can act. It loops: think, choose a tool, look at the result, decide the next step, until the task is done.

2. Why it matters

Many business tasks need several steps across systems (check a balance, book a meeting, send an email). An agent can do the steps; you control which tools it may use.

3. How it works

  • Chatbot: one question, one answer. Agent: a loop of decisions and tool calls.
  • Single agent: one model with tools. Multi-agent: several specialised agents hand work to each other.
  • Human-in-the-loop: a person approves risky actions such as sending money or emails.
  • Memory: short-term (this conversation) and long-term (saved facts, retrieved when needed).
  • Limits: wrong tool choices, loops that never end, and costs that grow with each step.

4. Practical implementation

File: tools/aihandbook/examples/05_agent_loop.py

# Week 3, Subjects 9-10: an agent loop with tools, tested with a scripted "model"
import json

TOOLS = {
    "get_leave_balance": lambda employee_id: {"employee_id": employee_id, "days_left": 14},
    "book_meeting": lambda title: {"status": "booked", "title": title},
}

def scripted_model(history):
    # A real model decides the next step. This script shows the decisions it would make.
    if not any(m["role"] == "tool" for m in history):
        return {"action": "tool", "name": "get_leave_balance", "args": {"employee_id": "E42"}}
    return {"action": "final", "text": "You have 14 days of leave left."}

def run_agent(user_request, max_steps=5):
    history = [{"role": "user", "content": user_request}]
    for step in range(max_steps):
        decision = scripted_model(history)
        if decision["action"] == "final":
            return decision["text"]
        result = TOOLS[decision["name"]](**decision["args"])
        history.append({"role": "tool", "content": json.dumps(result)})
        print(f"step {step + 1}: called {decision['name']} -> {result}")
    return "Stopped: step limit reached"

print("Answer:", run_agent("How much leave do I have left?"))

Expected output (produced by running the file)

step 1: called get_leave_balance -> {'employee_id': 'E42', 'days_left': 14}
Answer: You have 14 days of leave left.

5. Code explained

  • TOOLS is a registry: the agent may only call functions listed here.
  • max_steps stops a runaway loop.
  • Each tool result is added to history so the next decision can use it.

5b. Deep dive

Agent design questions to answer on paper before coding: what is the goal, which tools are allowed, what is the step limit, what must a human approve, what is logged, and when does the agent stop?

Planning styles: ReAct (think, act, observe in turns), plan-then-execute (write a plan, then carry it out), and router-plus-specialists (one agent picks which specialist handles the request).

Memory: short-term memory is the message history; long-term memory is a store you write to and search later (for example a notes table). Store only what is needed; personal data needs a retention rule.

Limits to test: the agent repeats a failing tool call, invents a tool result, or keeps going after the goal is met. Each needs a guard: step limits, validation of tool results, and a clear stop condition.

6. Testing

Run the file; the agent must call the tool once and then give a final answer.

7. Troubleshooting

  • Agent loops: lower max_steps and make tool descriptions clearer.
  • Wrong tool: improve the tool's name and description, and test each tool separately.

8. AI Product Manager perspective

  • Decide the autonomy level per action: suggest, draft, act with approval, or act automatically. Most enterprise launches start at 'suggest' or 'draft'.

9. Assignment

Add a third tool to the example (for example get_policy_text) and change scripted_model to use it. Print each step.

10. Interview preparation

Q: What is the difference between a chatbot and an agent?
A chatbot answers in one turn; an agent plans and uses tools over several steps until the goal is met.

Subject 10: Tool calling and agent development

Covered on the website   Week 3 · Core practical skills

1. Understand

Tool calling is giving the model a menu of functions with clear descriptions and input schemas. The model picks one and writes the arguments; your code runs it.

2. Why it matters

Without a clear schema, models pass wrong arguments or pick the wrong tool. Schemas are the contract between the model and your system.

3. How it works

  • Define each tool: name, description, typed inputs, and what it returns.
  • Validate inputs before running anything.
  • Execute, catch errors and return them to the model as results it can read.
  • Set permissions: which tools exist for which user.
  • Require approval for write actions (send, pay, delete).

4. Practical implementation

5. Code explained

  • **kwargs unpacks the model's arguments into the Python function.
  • Errors should be returned as text the model can act on, not crash the app.

5b. Deep dive

A tool schema is a JSON description: name, description, parameters with types and a list of required fields. The description is what the model reads to choose the tool, so write it like instructions for a new employee.

Validation: check every argument (type, range, allowed values) before executing. Reject unknown tools. Return errors as readable messages so the model can correct itself on the next step.

Permissions: separate read tools from write tools. Writes (send an email, change a record, spend money) need an approval step with a person, the proposed action, and a clear yes or no.

Logging: record the tool name, arguments, result summary, user, time and approval for each call. This is your audit trail and your debugging tool.

6. Testing

Give the agent a request it should refuse (a tool it does not have) and confirm it reports that instead of inventing a result.

7. Troubleshooting

  • Bad arguments: add type checks and examples in the description.
  • Unexpected writes: separate read tools from write tools and gate writes behind approval.

8. AI Product Manager perspective

  • A tool is a permission. Review each tool with security and legal before launch, as you would any new access to a system.

9. Assignment

Write a tool schema for 'create_support_ticket' with title, priority (low/medium/high) and customer_id. Validate priority and reject anything else.

10. Interview preparation

Q: How do you make tool calling safe?
Least-privilege tools, input validation, approvals for writes, logging every call and a step limit.

Subject 11: Model Context Protocol (MCP)

Covered on the website   Week 3 · Core practical skills

1. Understand

MCP is a standard plug. Instead of writing a custom connector for every AI app, a service exposes its tools once as an MCP server, and any MCP-capable AI app (the host) can use them.

2. Why it matters

It cuts integration work and makes permissions explicit. It is quickly becoming the common way AI tools connect to files, databases and SaaS apps.

3. How it works

  • Host: the AI app (Claude Code, an IDE, a chat app).
  • Client: the connector inside the host that speaks MCP.
  • Server: the service exposing Tools (actions), Resources (readable data) and Prompts (reusable templates).
  • MCP vs a normal API: an API is for code; MCP is designed for AI apps to discover and use capabilities.
  • MCP vs function calling: function calling is the model choosing a function; MCP is the standard way those functions are provided.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Each server should declare only the capabilities it needs.
  • Treat every MCP server as third-party code with access to data: review what it can read and write.

5b. Deep dive

MCP messages are JSON-RPC requests. A client asks a server what tools, resources and prompts it has, then calls them. Servers can run locally (stdio) or remotely (HTTP).

Resources are read-only data the host can attach to a conversation (a file, a database view). Tools perform actions. Prompts are reusable templates the user can pick.

Security questions for every MCP server: what data can it read, what can it change, which account does it act as, where are its logs, and who approved it? Prefer read-only servers for the first pilot.

MCP vs an API: an API is a contract for code written by developers; MCP is a contract designed for AI apps to discover capabilities at run time. You can wrap an existing API as an MCP server.

6. Testing

Connect a read-only MCP server to a host app and confirm it lists its tools and can answer a question about one resource.

7. Troubleshooting

  • Server not listed: check the configuration file path and restart the host.
  • Tool fails with permission errors: check the token scope.

8. AI Product Manager perspective

  • MCP shifts risk to access control. Write down which systems each agent can reach, who approved it, and how access is removed.

9. Assignment

Write a one-page security note for an MCP server that reads customer tickets: what it reads, what it may change, and how a human approves changes.

10. Interview preparation

Q: What problem does MCP solve?
It standardises how AI applications discover and use external tools and data, so each integration is built once instead of once per app.

Subject 12: Project: AI research agent

Partial on the website   Week 3 · Core practical skills

1. Understand

A research agent takes a topic, searches approved sources, reads what it finds, and writes a short report that cites each claim and notes disagreements.

2. Why it matters

Analyst time is expensive and research is repetitive. A good agent saves hours, but only if its sources and claims can be checked.

3. How it works

  • Define approved sources (a list of domains or documents).
  • Search, collect 5 to 10 results, and extract the relevant passages.
  • Summarise each finding with its source link.
  • Compare sources and flag conflicts.
  • Output a structured report: summary, findings, conflicts, sources, open questions.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Structured output (JSON with fixed keys) makes the report checkable by code.
  • A conflict list is more useful than a single smooth answer.

5b. Deep dive

Research agent pipeline: (1) plan the search queries, (2) search approved sources only, (3) fetch and extract passages, (4) score relevance, (5) summarise with citations, (6) compare claims across sources, (7) write the structured report.

Report schema: summary (3 sentences), findings (list of claim, source link, quote, confidence), conflicts (claim A vs claim B, sources), gaps (what was not found), and the date of each source.

Frameworks such as LangGraph model the same pipeline as a graph of steps with state, which helps when the agent branches or needs to resume. Start without a framework; add one when the plain loop gets hard to follow.

6. Testing

For 10 claims in the report, check each against its source. Count how many are supported.

7. Troubleshooting

  • Sources missing: require a link for every claim in the schema.
  • Summary drifts from the source: check quotes and add a grounding check.

8. AI Product Manager perspective

  • Define the user: an analyst who verifies, or an executive who reads. The answer format changes with the reader.

9. Assignment

Build the agent for one topic. Submit the report, the list of approved sources, and a table of claims checked against sources.

10. Interview preparation

Q: How would you evaluate a research agent?
Check claim accuracy against sources, source coverage, conflict detection and time saved per report.
