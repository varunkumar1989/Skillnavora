Subject 17: AI product discovery

Covered on the website   Week 5 · AI Product Management skills

1. Understand

Discovery is deciding what to build before building it. For AI, the first question is not 'can we use AI?' but 'does this problem need AI at all?'.

2. Why it matters

Many AI projects fail because the problem was never valuable, the data was not ready, or a simple rule would have worked better.

3. How it works

  • Find the problem: interview 8 to 10 users, observe their work, list pain points.
  • Use Jobs to be Done: 'When I ..., I want to ..., so that I ...'.
  • Test AI versus non-AI: could a rule, a form or a search solve it?
  • Check feasibility: data availability, accuracy needed, latency, privacy, cost.
  • Prioritise with impact, effort, risk and data readiness; compare build versus buy.
  • Write a business case: cost, benefit, ROI and payback.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Data readiness is often the blocker, not the model.
  • ROI for AI should include ongoing run cost and evaluation effort, not only build cost.

5b. Deep dive

Discovery methods: customer interviews (ask about the last time the problem happened), shadowing (watch the work), journey mapping, and a short survey to size the problem. Ask about behaviour, not about hypothetical features.

Jobs to be done format: 'When [situation], I want to [motivation], so I can [outcome].' It keeps the focus on the user's goal and shows which parts of the job AI can change.

Build vs buy vs rules: a rules engine or a search page may solve the problem in a week. AI earns its place when the input is free text, the judgement is fuzzy, and a 'good enough' answer is measurable.

Business case: benefit (hours saved x loaded cost x adoption rate + revenue effect), cost (build + run + evaluation + support over 12 to 24 months), risk (what if it is wrong), and the decision rule (go if payback is under the agreed period).

8. AI Product Manager perspective

Subject 18: End-to-end AI project: enterprise knowledge and research copilot

Partial on the website   Week 5 · Core practical skills

1. Understand

The capstone combines everything: documents (RAG), tools (agents), checks (evaluation), monitoring and a simple interface. You build it in stages, not in one pass.

2. Why it matters

This is how real AI products are built: a working slice first, then more features, each tested before the next.

3. How it works

  • Milestone 1: upload PDFs and answer questions with citations (Week 2 bot).
  • Milestone 2: add one tool, for example a web search with approved sources.
  • Milestone 3: add a research agent with a step limit and a structured report.
  • Milestone 4: add the 20-question evaluation and the cost and latency log.
  • Milestone 5: a simple Streamlit interface, deployed from GitHub with secrets in environment variables.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Stage gates: do not start milestone n+1 until milestone n passes its tests.
  • Keep a decision log: why each design choice was made.

5b. Deep dive

Stage gates: each milestone has a test list. Milestone 1 (chat with PDFs with citations) must pass 10 questions before tools are added. Milestone 2 (one tool) must not break milestone 1's tests.

Architecture to draw in your README: user interface, API layer, retrieval, model calls, tools, storage, logs and evaluation. Mark where data leaves your system (for example to a model provider).

Deployment checklist: secrets in the host's settings, a health check page, a fixed dependency file, a sample dataset that is not confidential, and a privacy note in the README.

Portfolio evidence: the repository, the README with a demo link, the PRD, the evaluation report (20 questions with scores), a cost and latency table, and a three-minute recording.

10. Interview preparation

Q: How would you scope an AI product for the first release?
Pick the smallest workflow that delivers measurable value, define the quality bar, and defer features that do not test a key assumption.

Subject 19: AI product documentation

Covered on the website   Week 5 · AI Product Management skills

1. Understand

Product documents turn an idea into a shared plan: why we build it, for whom, what it must do, how we will know it works, and what could go wrong.

2. Why it matters

AI projects involve data, engineering, legal and business teams. A clear PRD prevents months of arguing about what 'done' means.

3. How it works

  • Write the problem statement and target users with two personas.
  • Describe the user journey and the AI-specific moments (where the AI answers, where a human approves).
  • Write functional and non-functional requirements (latency, privacy, availability, accuracy).
  • Write user stories and acceptance criteria.
  • Add architecture, data flow, evaluation strategy, risk register, success metrics and a roadmap.
  • Use the PRD template in Part G.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • Acceptance criteria for AI must include quality thresholds, not only features.
  • The risk register must include hallucination, data leakage and cost overrun.

5b. Deep dive

PRD sections and what each must answer: problem (who, what pain, how often), users (two personas with goals and constraints), journey (where AI helps and where a person decides), requirements (testable), quality bar (numbers), data (sources, owners, permissions), risks (likelihood, impact, mitigation), and success metrics (baseline and target).

Writing testable requirements: 'The bot answers from approved sources and shows at least one citation for 95 percent of answers on the golden set' is testable; 'the bot is accurate' is not.

Decision log: record each important decision, the options, the trade-off and the date. Future you (and your reviewers) will ask why.

Subject 20: Deployment, GitHub and portfolio

Partial on the website   Week 5 · Core practical skills

1. Understand

Deployment means putting your app where others can use it. GitHub stores the code and the history; Streamlit or a cloud host runs it.

2. Why it matters

A deployed link and a clean repository are what hiring managers look at first. A notebook on your laptop is not a portfolio.

3. How it works

  • Repository structure: app/, tests/, data/ (sample only), README.md, requirements.txt, .env.example.
  • Never commit secrets: add .env to .gitignore; use .env.example for names only.
  • Write a README: problem, demo link, architecture diagram, setup steps, evaluation results.
  • Deploy: Streamlit Community Cloud or a similar free host, with secrets set in the host's settings.
  • Demo recording: 3 minutes, showing one real question and its citation.

4. Practical implementation

Work through the steps above and keep the result in your portfolio repository.

5. Code explained

  • requirements.txt pins the libraries your app needs.
  • Docker packages the app and its environment; learn the idea first, the commands second.

5b. Deep dive

Repository layout: app/ (code), tests/, data/sample/ (non-confidential), docs/ (PRD, architecture), README.md, requirements.txt, .env.example, .gitignore.

Git workflow for beginners: git init, git add, git commit -m 'message', git push. Commit small, tested steps with clear messages. Never commit .env files or keys.

Deployment options: Streamlit Community Cloud (connect the GitHub repository, set secrets in the settings), Hugging Face Spaces, or a container on a cloud provider. Docker packages the environment so it runs the same everywhere.
