How Software Applications Work :: A user interacts with a front end, which sends requests to back-end services. Those services apply business rules, read and write data and return results. Knowing this flow helps a PM describe where a bug or delay happens.
Software Development Lifecycle (SDLC) :: The SDLC covers planning, design, build, test, deploy and maintain. It can run in sequence or iteratively. Each stage has outputs such as requirements, designs, code and release notes that the PM reviews.
Frontend Fundamentals :: Frontend code (HTML, CSS and JavaScript on the web, or native code on mobile) controls what users see and touch. Performance on frontend depends on page weight, rendering and network requests.
Backend Fundamentals :: The back end runs server logic, business rules, databases and integrations. Latency and reliability problems often start here, so PMs should understand what runs on the back end and what each request costs.
Client-Server Architecture :: Clients send requests and servers process them and send responses over a network. Most apps follow this pattern. Consider where data is processed when designing offline or low-bandwidth features.
Databases and Data Storage :: Databases persist application data. The choice depends on structure, scale, consistency and query needs. Changing a database later is expensive, so involve engineers early in data decisions.
SQL and NoSQL Databases :: SQL databases store structured tables with strong consistency and joins. NoSQL covers document, key-value, column and graph stores that trade some consistency or queryability for flexibility and scale.
Relational Database Concepts :: Relational databases use tables, keys, relationships and normalisation. Transactions follow ACID properties (atomicity, consistency, isolation, durability), which keep money movements correct.
APIs and API Fundamentals :: An API is a contract that lets software components communicate. It defines requests, responses, authentication and error behaviour. Good APIs are stable and documented, because other teams depend on them.
REST APIs :: REST exposes resources through HTTP verbs such as GET, POST, PUT and DELETE, and uses status codes to report results. Example: GET /orders/123 returns one order.
GraphQL :: GraphQL lets clients request exactly the fields they need from a single endpoint. It reduces over-fetching for complex screens but needs care with query cost and caching.
Webhooks :: A webhook sends an HTTP request from one system to another when an event occurs, such as payment succeeded. It avoids constant polling, but the receiver must handle retries and duplicate events.
Authentication and Authorisation :: Authentication proves identity, for example with a password or single sign-on. Authorisation decides what that identity may do, using roles or permissions. OAuth is a common standard for delegated access.
JSON and XML :: JSON and XML are text formats for structured data. JSON is lighter and standard for web APIs. Knowing the format helps a PM read API responses and specifications.
API Documentation :: Good documentation includes reference pages, guides and examples, often generated from an OpenAPI specification. Clear docs cut support requests and speed up integration.
Postman :: Postman lets you send requests, inspect responses and save collections of API calls. PMs use it to understand how an API behaves before writing requirements.
Git and GitHub Fundamentals :: Git tracks changes to code. GitHub hosts repositories and supports pull requests and code review. Knowing the basic workflow lets a PM follow release discussions and documentation changes.
Version Control :: Version control records history so teams can collaborate, branch, review and roll back. Rollbacks depend on it, and it is the audit trail for what changed in each release.
Microservices Architecture :: Microservices split an application into small, independently deployable services that talk over APIs. They help large teams work in parallel, but add operational complexity and network failure modes.
Monolithic Architecture :: A monolith is one deployable unit containing all functionality. It is simpler to start and debug, but large teams can slow each other down. Many successful products begin as monoliths.
System Design Fundamentals :: System design chooses components, data flows and trade-offs to meet requirements for scale, cost and reliability. PMs do not design systems alone, but they should know which trade-offs their requirements create.
Scalability and Reliability :: Scalability handles growing load, and reliability keeps the service available despite failures. Techniques include redundancy, caching, load balancing and graceful degradation, such as showing cached data when a service is slow.
Latency and Throughput :: Latency is the time for one request. Throughput is the number of requests handled per unit time. A system can have high throughput and poor latency, so track both.
Cloud Computing Fundamentals :: Cloud services provide compute, storage and managed services on demand, paid by use. Models include IaaS, PaaS and SaaS. Responsibility for security is shared between provider and customer.
AWS Fundamentals :: AWS offers services such as EC2 for virtual machines, S3 for storage, Lambda for functions, RDS for managed databases and IAM for access control. Knowing these names helps in technical discussions.
Microsoft Azure Fundamentals :: Azure provides virtual machines, storage, Azure Active Directory for identity, Azure OpenAI for model access and DevOps tools. Many enterprises already use Azure, which affects procurement and integration choices.
Google Cloud Platform Fundamentals :: GCP offers Compute Engine, Cloud Storage, BigQuery for analytics and Vertex AI for machine learning. Its data and AI services are often chosen for analytics-heavy products.
Cybersecurity Fundamentals :: Security covers confidentiality, integrity and availability, plus encryption, secure coding, access control and common attacks. A PM must treat security requirements as product requirements, not as later clean-up.
