Product Requirement Document (PRD) :: A PRD describes the problem, target users, goals, scope, requirements, success metrics and launch plan. It is a shared reference for teams, not a contract. Keep it short and link to research and designs rather than copying them in.
Business Requirement Document (BRD) :: A BRD captures business needs, objectives, scope and constraints, usually for sponsors and finance. It answers why the business should invest. The PRD then explains what the product will do to deliver that business case.
Functional Requirements :: Functional requirements describe what the system must do, such as "a user can reset a password by email". Write each one so it can be tested. Vague phrases such as "easy to use" are not functional requirements.
Non-Functional Requirements :: These describe how well the system must perform: response time, availability, security, scalability and compliance. Quantify them, for example "99.9% uptime per month" or "search returns in under 300 ms for 95% of queries".
Technical Requirements :: Technical requirements cover architecture, integrations, data formats, platforms and infrastructure. Engineers should review them early, because they often change cost and timeline. Include constraints such as data residency rules.
Product Specifications :: Specifications describe behaviour, rules, data and interfaces in enough detail to build and test the feature. Include edge cases, validation rules and examples. A good spec reduces questions during development.
Epics, Features and User Stories :: An epic is a large goal, a feature is a deliverable capability, and a user story is a small, user-centred slice that fits in one sprint. Example: "Faster payouts" as an epic, "Instant payout request" as a feature, and "As a seller, I can request a payout from my dashboard" as a story.
User Story Mapping :: Story mapping arranges stories along the user journey, with the most important path at the top. Slice releases horizontally so each release delivers a usable end-to-end path rather than half of many features.
Acceptance Criteria :: Acceptance criteria are specific, testable conditions a story must meet. The Given/When/Then format is common: given a verified account, when the user requests a payout above the limit, then the system shows the limit message.
Definition of Ready :: The checklist a story must meet before the team starts work: clear value, acceptance criteria, dependencies identified and design available. It prevents half-understood work entering a sprint.
Definition of Done :: The shared quality bar every item must meet: tested, reviewed, documented, monitored and deployable. Without it, items are called done before they are safe to release.
Use Cases :: A use case describes how an actor achieves a goal with the system, including alternative paths and failures. Use cases are useful for complex workflows such as loan approval, where many roles and rules interact.
Edge Cases :: Edge cases are rare or extreme inputs and states, such as an empty cart, a very large file or a timeout during payment. Ask what happens when inputs are empty, huge, slow or invalid. Many production bugs live in these cases.
Error Scenarios :: Error scenarios describe how the product behaves when something fails, including the message shown, the recovery path and what is logged. Good error handling tells the user what to do next.
Product Backlog Creation :: The backlog is a prioritised list of everything that might be built. Each item needs a clear description and an expected value. Keep the backlog honest by removing items that no longer matter.
Backlog Refinement :: Refinement regularly clarifies, splits, estimates and orders backlog items so the next sprints are ready. Refine two to three sprints ahead. Items should be small enough to finish within one sprint.
Release Documentation :: Release notes, change logs, runbooks and support guides explain what changed and how to operate it. Support teams need these before launch, not after the first customer complaint.
Product Requirement Traceability :: Traceability links each requirement to its goal, design, tests and release. It shows that every requirement is covered and helps assess the impact of a change. Use a simple table or tool, and keep it current.
Technical Documentation :: Architecture notes, API references and runbooks let others build, integrate and support the product. Keep them next to the code so they are updated with it.
Product Decision Records :: A decision record notes the decision, the options considered, the reason and the expected consequences. Months later, people can see why a choice was made instead of re-arguing it.
