ML metrics (15)

How to score models. TP, FP, FN and TN are true positives, false positives, false negatives and true negatives.

ItemWhat it doesExample

PrecisionTP ÷ (TP + FP): of predicted positives, how many were right32 ÷ 50 = 64%
Recall (sensitivity)TP ÷ (TP + FN): of actual positives, how many were found32 ÷ 40 = 80%

SpecificityTN ÷ (TN + FP)Share of genuine non-fraud correctly cleared

PR-AUCArea under the precision-recall curve; better for rare positivesFraud, rare defects
Log lossPenalises confident wrong probabilitiesLower is better

RMSERoot mean squared error: punishes large errors moreRMSE ≥ MAE always
MAPEMean absolute percentage errorAvoid when actual values can be near zero

A1 Data Engineering Fundamentals

A1.1 What data engineering is and the roles

What is it?

Data engineering builds and runs the systems that move, store and prepare data so analysts, data scientists and AI applications can use it reliably.

Why is it important?

Without reliable pipelines, dashboards show wrong numbers and models train on stale data. Engineers own that reliability.

Where is it used in industry?

Banks, retailers, SaaS companies and AI product teams all employ data engineers to feed their reporting, ML and AI features.

How does it work?

  • Sources (apps, databases, APIs, files) produce raw data.
  • Ingestion copies it into a landing zone.
  • Transformation cleans and models it.
  • Serving gives analysts and models trusted tables.

Practical example

A sales app writes orders to a database; a nightly pipeline copies them to a warehouse and builds a daily revenue table that the Power BI dashboard reads.

Tool or software

Any SQL client and Python

Treating a data engineer as a 'report builder'. Their work is the reliability and repeatability of the flow.

A1.2 Data types and file formats: CSV, JSON, XML, Parquet, Avro, ORC

What is it?

A file format is the way data is written to disk. Row formats (CSV, JSON, Avro) store records one after another; column formats (Parquet, ORC) store each column together.

Why is it important?

Column formats read faster and smaller for analytics, and compression cuts storage cost. Choosing the wrong format is a common cause of slow, expensive pipelines.

Where is it used in industry?

Data lakes and warehouses commonly store Parquet; Kafka pipelines often use Avro with a schema registry.

How does it work?

  • CSV: plain text, no types, easy to read.
  • JSON: nested, flexible, larger.
  • Parquet and ORC: columnar, typed, compressed, best for analytics.
  • Avro: row format with a schema, common for streams.
  • Compression (Snappy, gzip, zstd) trades CPU for size.

Practical example

A 2 GB CSV of transactions becomes about 250 MB as Parquet, and a query summing one column reads only that column.

Tool or software

pandas, DuckDB

Hands-on exercise

Convert a CSV of 1 million rows to Parquet and compare file size and the time to sum one column.

Common mistakes

Storing everything as CSV because it is familiar, then wondering why queries are slow.

A1.3 Ingestion: batch, streaming, API, file, database and CDC

What is it?

Ingestion is the step that brings data from sources into your platform. Batch loads chunks on a schedule; streaming sends events as they happen; CDC (change data capture) reads database changes from the transaction log.

Why is it important?

The ingestion method decides freshness, cost and risk of missed or duplicated records.

Where is it used in industry?

Fraud teams use streaming; finance reporting usually uses daily batch; inventory systems often use CDC from the operational database.

How does it work?

  • Batch: scheduled pull of new or changed rows (often by an updated_at column).
  • Streaming: events published to a topic and consumed continuously.
  • API: paginated pulls with rate limits and tokens.
  • CDC: reads inserts, updates and deletes from the database log.

Practical example

An API returns orders in pages of 100; the pipeline stores the last updated timestamp and asks only for newer orders next run.

Tool or software

Python requests, Airbyte (open source connectors), Debezium for CDC

Hands-on exercise

Common mistakes

Pulling the whole table every night when only changes are needed.

A1.4 ETL versus ELT

What is it?

ETL extracts, transforms outside the target, then loads. ELT extracts and loads raw data first, then transforms it inside the warehouse.

Why is it important?

ELT is common on cloud warehouses that have cheap, fast compute, and keeps raw data for re-processing. ETL still fits when data must be cleaned or masked before it lands.

Where is it used in industry?

Most modern analytics teams use ELT with dbt; regulated teams may use ETL to remove personal data before loading.

How does it work?

  • ETL: transform in a separate engine, then load clean tables.
  • ELT: load raw tables first (for example in a raw schema), then SQL models build the clean layers.
  • Keep the raw data so models can be rebuilt.

Raw Shopify orders load into a raw schema; a dbt model builds a cleaned orders table and a daily revenue table.

A1.5 Pipeline reliability: idempotency, retries, incremental loads

What is it?

An idempotent pipeline gives the same result when run twice. Incremental loads process only new or changed data. Retries repeat a failed step with a wait between attempts.

Why is it important?

Pipelines fail and are re-run. Without idempotency, a re-run creates duplicate sales and wrong totals.

Where is it used in industry?

Every production pipeline in finance, e-commerce and logistics must survive reruns and partial failures.

How does it work?

  • Use MERGE or upsert keyed on a business key instead of plain INSERT.
  • Load into a staging table, validate, then swap or merge.
  • Store a run ID and watermark so reruns know where they stopped.
  • Retry transient errors (timeouts) with exponential backoff; fail fast on bad data.

Practical example

A nightly job merges orders on order_id; running it twice still leaves one row per order.

Tool or software

SQL MERGE or INSERT ... ON CONFLICT (PostgreSQL)

Hands-on exercise

Common mistakes

Using INSERT for a daily load, so reruns duplicate rows.

A1.6 Data modelling: conceptual, logical, physical; star and snowflake schemas

What is it?

Conceptual models name the business entities; logical models add attributes and keys; physical models are the actual tables. A star schema has one fact table of measures and dimension tables describing them.

Why is it important?

A clear model makes queries simple and consistent, so two teams get the same revenue number.

Where is it used in industry?

Almost every BI platform (Power BI, Tableau, Looker) works best on a star schema.

How does it work?

  • Fact table: sales lines with amount, quantity and foreign keys.
  • Dimension tables: customer, product, date, store.
  • Snowflake schema normalises dimensions further (more joins, less duplication).

A1.7 Slowly Changing Dimensions (SCD) types 1, 2 and 3

What is it?

A slowly changing dimension is an attribute that changes over time, such as a customer's city. Type 1 overwrites it; Type 2 keeps history with valid-from and valid-to dates; Type 3 keeps one previous value.

Why is it important?

Reports about past periods must use the value that was true then. Type 2 makes that possible.

Where is it used in industry?

Customer, employee and product history in banks, HR systems and retailers depend on SCD Type 2.

How does it work?

  • Type 1: update the row; history is lost.
  • Type 2: close the old row (valid_to) and insert a new row with a new surrogate key.
  • Type 3: add a column for the previous value.

Practical example

A customer moves from Pune to Bengaluru on 1 Jan; the old row ends on 31 Dec and the new row starts on 1 Jan, so last year's sales still show Pune.

A2 Data Warehousing, Lakes and Lakehouses

A2.1 Data warehouse, data mart, data lake and lakehouse

What is it?

A data warehouse stores cleaned, structured data for reporting. A data mart is a warehouse slice for one department. A data lake stores raw files of any type cheaply. A lakehouse adds warehouse features (tables, ACID transactions, SQL) on top of lake storage.

Choosing the right storage decides cost, speed and who can use the data.

Where is it used in industry?

Raw clickstream JSON sits in the lake; cleaned sessions go to the warehouse for BI.

A2.2 Medallion architecture: bronze, silver and gold

What is it?

Medallion architecture organises a lakehouse or warehouse in three layers: bronze (raw, as received), silver (cleaned and conformed), gold (business-ready tables and metrics).

Why is it important?

Each layer has one job, so bugs are found and fixed in one place, and analysts use only trusted gold tables.

Used widely on Databricks, Microsoft Fabric and by dbt-based teams.

How does it work?

  • Bronze: append raw data with load time and source.
  • Silver: deduplicate, fix types, apply keys and quality rules.
  • Gold: aggregates and star schemas for dashboards and models.

B2.1 Recursive CTEs and hierarchies

What is it?

B11 OLTP vs OLAP in Depth (Module 2 gap)

B11.1 OLTP and OLAP: two kinds of database work

What is it?

OLTP (online transaction processing) systems record many small, fast changes; OLAP (online analytical processing) systems answer big questions over lots of history.

Why is it important?

Running heavy reports on the app database slows the app for customers; designing an analytics model like an app database makes reports slow and complex.

Where is it used in industry?

Every product company has both: the app's database (OLTP) and a warehouse or lakehouse for reporting (OLAP).

How does it work?

  • OLTP: many users, single-row reads and writes in milliseconds, normalised tables, row storage, strict transactions (ACID). Examples: PostgreSQL, MySQL, SQL Server for an app.
  • OLAP: fewer users, queries over millions of rows, denormalised star schemas, columnar storage, data refreshed in batches or streams. Examples: BigQuery, Snowflake, Redshift, Fabric, Databricks SQL.
  • Data moves from OLTP to OLAP through ETL or ELT pipelines, often with change data capture.
  • Some databases handle both (HTAP), but most teams still separate the workloads.

Practical example

A food-delivery app writes each order to PostgreSQL (OLTP). Every night the orders flow into BigQuery (OLAP), where a star schema answers 'revenue by city by week' in seconds.

Tool or software

PostgreSQL or MySQL for OLTP; BigQuery, Snowflake or DuckDB for OLAP practice

Hands-on exercise

Take an orders schema in third normal form and redesign it as a star schema with one fact table and three dimensions. List which queries get simpler.

Common mistakes

Running month-end reports directly on the production database during business hours.

B14.2 Worked case: risk analysis with expected value and simulation

What is it?

Quantifying risk by combining how likely something is with how much it would cost, and simulating many possible outcomes.

Why is it important?

Turns vague worries into numbers that can be compared and prioritised.

Where is it used in industry?

Credit risk in lending, supply risk in operations, project risk and insurance.

How does it work?

  • List risks; estimate probability and impact for each.
  • Expected loss = probability × impact; rank risks by expected loss.
  • Where inputs are uncertain, use a range and run a Monte Carlo simulation (thousands of random draws).
  • Report the average and a bad-case percentile (for example the 95th) of the simulated loss.
  • Revisit estimates as real data arrives.

Practical example

A supplier delay has a 10% chance and ₹20 lakh impact (expected loss ₹2 lakh); a data breach has a 1% chance and ₹5 crore impact (expected loss ₹5 lakh), so the breach is the higher priority.

What is idempotency?A pipeline is idempotent if running it twice leaves the same result. Use MERGE on a business key, staging tables and run IDs.
Batch vs streaming?Batch processes data in scheduled chunks with simpler tooling. Streaming processes events continuously for low latency, at higher complexity. Choose by the freshness the business needs.
Star vs snowflake schema?A star schema has denormalised dimensions and simple joins, which is fast for BI. A snowflake normalises dimensions, saving space and adding joins.
What is a surrogate key and why use it?A system-generated key for a dimension row, so history (SCD Type 2) and source key changes do not break facts.
How do you handle late-arriving data?Reprocess the affected window (backfill), use watermarks that allow a lag, and make loads idempotent.
What does a dbt test check?Built-in tests check not null, unique, accepted values and relationships; custom tests are SQL queries that should return zero rows.
What is Airflow used for?Scheduling and monitoring workflows as DAGs with dependencies, retries and alerts. It does not process large data itself.
Spark shuffle and partitions?A shuffle moves data between machines during joins and groupBy; reduce it with good partitioning, broadcast small tables and avoid skew.
Warehouse vs lakehouse?A warehouse is optimised for SQL on structured data; a lakehouse adds open table formats on cheap storage for both files and SQL.
How do you test a data pipeline?Unit tests for transformations, data tests for quality, contract tests for source schemas, and a staging run compared with production totals.
What is CDC?Change data capture reads inserts, updates and deletes from a database log, so downstream systems stay current without full reloads.

C2 Seven Business Scenario Interviews (with answer frameworks)

ItemAnswer
Sales declined by 20%. How would you investigate?Clarify the period and the scope. Check data quality first (did the data load fully?). Split the decline by region, product, channel, customer segment and price. Compare with last year and with marketing and stock events. Form two or three hypotheses, test each, and recommend actions with expected impact.
Customer churn increased. What would you analyse?Define churn precisely. Build cohorts and see which cohorts churn. Compare churned and retained customers on usage, support tickets, price changes and product fit. Check onboarding funnel drop-offs. Recommend an experiment, not a guess.
A dashboard is slow. How would you optimise it?Find the slow visuals and queries. Reduce the data model (remove unused columns, aggregate at the right grain), use summary tables or incremental refresh, simplify DAX or SQL, check relationships and cardinality, and cache where the platform allows.
A data pipeline failed. How would you troubleshoot?Confirm impact and mitigate (re-run or stop downstream). Read the first error, check upstream freshness and schema changes, reproduce on a sample, fix the root cause, add a test or alert, and write a short review.
An AI assistant gives incorrect answers. How would you investigate?Log the exact prompt, retrieved context and model version. Check whether the right documents were retrieved. Compare answers with a labelled test set. Separate retrieval failures from generation failures. Add failing cases to the evaluation set and fix the cause.
An enterprise customer wants to automate a manual workflow. How would you design it?Map the current process and the exceptions. Pick the high-volume, low-risk steps to automate first. Design the flow with systems, data, approvals for risky actions, logging and fallbacks. Pilot with success metrics, then scale.
A stakeholder asks for a dashboard but cannot define requirements. How would you proceed?Ask about the decision the dashboard supports, who uses it and how often. Sketch two or three mock screens, get feedback, agree the first five metrics and a definition for each, then build a first version in a short cycle.
